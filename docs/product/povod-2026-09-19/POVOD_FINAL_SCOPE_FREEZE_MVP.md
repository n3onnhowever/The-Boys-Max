# 1. Главный принцип

**Повод — solo-first продукт.**

Пользователь должен получить полноценную ценность один:
1. открыть mini-app внутри MAX;
2. автоматически войти через MAX identity;
3. задать интересы и условия;
4. получить подходящие реальные события;
5. открыть конкретный occurrence;
6. увидеть дату, время, место, цену либо честный `UNKNOWN`, источник и ограничения;
7. открыть первоисточник;
8. при желании сохранить событие.

Социальный сценарий **не является обязательным** для прохождения основного пути.

---

# 2. Обязательный E2E-сценарий

## Must-pass flow

`MAX → Повод → MAX identity → интересы/условия → персональная афиша → конкретное событие → detail occurrence → источник`

### Обязательные шаги
1. Пользователь открывает «Повод» из MAX.
2. Backend валидирует MAX identity.
3. Создаётся или загружается существующий `PovodUser`.
4. Пользователь выбирает интересы и основные ограничения: дата/период, время, бюджет, при наличии район/локацию.
5. Система получает **живые данные** из реально подключённого источника.
6. Пользователь видит список подходящих событий.
7. Каждая карточка относится к конкретному `Occurrence`.
8. Пользователь открывает detail.
9. Detail показывает событие, конкретную дату, время, площадку/место, цену (`exact / from / range / free / unknown`), источник и предупреждения.
10. Пользователь может открыть первоисточник.
11. Пользователь может сохранить событие.
12. Основной сценарий считается завершённым **без группы и без приглашения друзей**.

# 3. P0 — обязателен к сдаче

## 3.1. MAX identity
- бесшовный вход;
- серверная валидация platform identity;
- без email/password;
- без обязательного телефона;
- повторный вход возвращает того же пользователя.

## 3.2. Один реально работающий город
**Основной demo city: Москва.**

Требование:
- живые данные;
- фактический coverage;
- data gate;
- нельзя заменять отсутствие данных ручными декоративными карточками.

Архитектура остаётся multi-city, но MVP не блокируется отсутствием второго города.

## 3.3. Живой event provider
Минимум один реально работающий provider adapter.

Provider должен давать достаточно данных для:
- события;
- occurrence;
- даты/времени;
- места;
- цены либо честного `UNKNOWN`;
- первоисточника.

## 3.4. Персональная афиша
Экран **«Для тебя»**:
- interests;
- structured filters;
- explainable reasons;
- event cards;
- save.

## 3.5. Поиск и фильтры
Обязательно:
- дата/период;
- категория;
- бюджет;
- время;
- город технически;
- текстовый поиск, если поддерживается источником/индексом.

Natural-language / LLM input **не обязателен**.

## 3.6. Event detail
Обязательно:
- title;
- category;
- occurrence date;
- start time;
- end time, если известно;
- venue;
- address, если известно;
- price state;
- source;
- source URL;
- `UNKNOWN` state;
- CTA `Открыть источник`.

Не использовать `Купить билет`, если покупки внутри «Повода» нет.

## 3.7. Сохранённые
Минимум:
- сохранить;
- удалить из сохранённых;
- увидеть сохранённое после повторного входа;
- ended/unavailable state не исчезает молча.

## 3.8. «Мой Повод»
Базовый профиль:
- MAX identity;
- домашний город;
- интересы;
- бюджет;
- обычное время;
- сохранённые настройки.

Без сложной аналитики профиля.

## 3.9. Honest states
Обязательно реализовать:
- loading;
- empty;
- source unavailable;
- validation error;
- general error;
- `UNKNOWN`;
- ended/stale occurrence.

`UNKNOWN` никогда не превращается в 0 / false / «всё ок».

## 3.10. MAX mobile + web
Основной flow должен работать:
- в MAX mobile;
- в MAX web.

Минимальная responsive-проверка:
- 360 px;
- 390 px;
- 430 px;
- web viewport.

# 4. P1 — делать только после стабильного P0

P1 не должен задерживать core.

## 4.1. Базовые подписки
Минимум один тип:
- `artist` **или**
- `topic`.

Допустимо сделать оба, если это не увеличивает срок существенно.

## 4.2. Один настоящий «Умный Повод»
End-to-end сценарий:

`follow → новое релевантное событие → бот MAX → deep link/startapp → exact occurrence`

Сообщение должно опираться на реальные данные:
- артист/тема;
- дата;
- время;
- цена либо UNKNOWN;
- город;
- причина соответствия.

## 4.3. Карта
Карта входит в P1, если:
- provider даёт координаты;
- реализация не тормозит основной flow.

Если карты нет, detail всё равно обязан показывать место и адрес.

# 5. Stretch

Stretch реализуется только после прохождения P0 acceptance.

## 5.1. Второй город
Например Санкт-Петербург.

Условие:
- отдельный data gate;
- тот же provider adapter contract;
- без hardcoded fork архитектуры.

Второй город нужен как **proof of scalability**, а не как обязательный объём данных.

## 5.2. Shared plan / «Позвать друзей»
Optional social continuation.

Путь:
`detail → Позвать друзей → plan_id → share/deeplink/startapp → участник открывает тот же план`

Не строить flow вокруг программного добавления пользователей в групповой чат.

Минимальная shared logic:
- event/occurrence snapshot;
- preference yes/maybe/no;
- explicit commitment отдельно;
- material change → re-confirmation.

# 8. Критерии готовности MVP

- [ ] новый пользователь проходит flow;

# 9. Definition of Done

**Hackathon MVP = DONE**, когда одновременно верно:

> Реальный пользователь открывает «Повод» внутри MAX, автоматически определяется через MAX identity, задаёт свои условия, получает живые события Москвы, открывает конкретный occurrence с честными данными и источником, может сохранить его, а приложение стабильно проходит тот же flow в MAX mobile и web с корректными состояниями loading / empty / error / UNKNOWN.

Всё остальное — улучшение, а не условие существования продукта.

---

# 10. Freeze rule

После этого документа P0 считается **замороженным**.

Любая новая идея до сдачи проходит один вопрос:

> **Она необходима для обязательного solo E2E или исправляет критический риск?**

Если нет:
- переносится в P1;
- либо в Stretch;
- либо после хакатона.

Новые функции не добавляются в P0 без явного пересмотра scope freeze всей командой.
